# log-engine

Быстрый многопоточный парсер и анализатор логов на C++20. Читает файл через `mmap`, разбирает строки без копирования и аллокаций, делит работу между потоками без мьютексов и выдаёт отчёт: уровни, самые шумные сервисы, самые частые ошибки, перцентили задержек.

https://github.com/user-attachments/assets/3af23a98-dbe2-440c-94e5-b94c1fb22a17

## Результат

Тестовый лог: 5 млн строк, 352 МиБ, 12 логических потоков, файл в кэше ОС (Windows 11, GCC 16.2 `-O2`).

| Режим | Время | Скорость |
|---|---|---|
| 1 поток | 0,56 с | 624 МиБ/с · 8,9 млн строк/с |
| 12 потоков | 0,085 с | 4,1 ГиБ/с · 58,6 млн строк/с |

Ускорение ×6,6 на 12 потоках. С холодного диска скорость будет ограничена самим диском.

## Что считает

Пример вывода на тестовом логе:

```
== Summary ==
lines        : 5000000 (malformed 99434, matched 4900566)
time range   : 2026-10-01T00:00:00.001Z .. 2026-10-01T03:28:20.159Z

== Levels ==
INFO      3431598
WARN       439598
ERROR      269499
FATAL       14711

== Latency (took=Nms), 4900566 samples ==
p50 25  p90 45  p95 47  p99 49  p99.9 2724 ms

== Top components ==
component                       count     errors     avg ms   max ms
cache                          409296      23842       39.5     3034
payments                       408982      23783       39.6     3040

== Top errors ==
     71315  db timeout after
     70972  null pointer in handler
```

Перцентили (p50, p90, p99, p99.9) показывают «хвост» задержек: среднее здесь около 40 мс, а один запрос из тысячи висит почти 3 секунды.

## Формат лога

```
2026-10-01T12:34:56.789Z INFO  auth-service  login ok user=42 took=12ms
```

Время (UTC, ровно 24 символа), уровень (`TRACE DEBUG INFO WARN ERROR FATAL`), сервис, сообщение. Фрагмент `took=NNNms` в сообщении используется для статистики задержек. Строки другого формата считаются битыми и учитываются отдельным счётчиком. Парсер изолирован в [`parser.hpp`](include/le/parser.hpp), поддержку других форматов (nginx, JSON, syslog) можно добавить, не трогая остальной код.

## Сборка

Нужен компилятор с C++20 (GCC 10+, Clang 12+, MSVC 2019 16.11+) и CMake 3.16+.

```bash
git clone https://github.com/thirteenbtw/log-engine.git
cd log-engine
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release
```

Без CMake (проверено на GCC/MinGW):

```bash
g++ -std=c++20 -O2 -static -Iinclude src/main.cpp -o logengine
g++ -std=c++20 -O2 -Iinclude tools/gen_logs.cpp -o gen_logs
```

## Использование

```bash
gen_logs sample.log 5000000        # сгенерировать тестовый лог (~350 МиБ)
logengine sample.log               # все ядра
logengine sample.log -t 1          # один поток (для сравнения)
logengine sample.log --level ERROR --component payments --top 5
logengine sample.log --grep timeout --from 2026-10-01T01:00:00.000Z --to 2026-10-01T02:00:00.000Z
```

| Опция | Назначение |
|---|---|
| `-t`, `--threads N` | число потоков (по умолчанию все ядра) |
| `--chunk-mb N` | размер чанка в МиБ (по умолчанию 4) |
| `--level L` | минимальный уровень: `TRACE DEBUG INFO WARN ERROR FATAL` |
| `--component C` | только этот сервис |
| `--grep S` | только сообщения, содержащие подстроку `S` |
| `--from TS`, `--to TS` | интервал времени, формат `YYYY-MM-DDTHH:MM:SS.mmmZ` |
| `--top N` | длина топ-списков (по умолчанию 10) |

Фильтры применяются до подсчёта, поэтому все показатели (включая перцентили) строятся по выборке.

## Как это работает

```
файл ──mmap──► один массив байт
                    │
        чанки по 4 МиБ, границы выровнены по '\n'
                    │
   поток 1   поток 2   …   поток N     каждый берёт следующий чанк
      │         │              │       через один atomic-счётчик
 свой Stats  свой Stats     свой Stats  (без блокировок)
      └─────────┴──────┬───────┘
                  слияние → отчёт
```

| Приём | Где |
|---|---|
| `mmap` / `MapViewOfFile`: файл не копируется в буфер | [`mapped_file.hpp`](include/le/mapped_file.hpp) |
| Zero-copy: все поля это `string_view` в память файла, ключи хэш-таблиц тоже | [`parser.hpp`](include/le/parser.hpp) |
| Ручной разбор времени, алгоритм `days_from_civil` вместо `strptime` | [`time_util.hpp`](include/le/time_util.hpp) |
| Чанки выровнены по `\n`: строка принадлежит чанку, где она начинается | [`engine.hpp`](include/le/engine.hpp) |
| Статистика на поток (`alignas(64)` против false sharing), слияние один раз в конце | [`stats.hpp`](include/le/stats.hpp) |
| Хэш-таблица с открытой адресацией, один массив слотов | [`flat_map.hpp`](include/le/flat_map.hpp) |
| Гистограмма задержек фиксированного размера, точные перцентили до 10 с | [`stats.hpp`](include/le/stats.hpp) |

На строку не выделяется память: аллокации происходят только при создании потоков, росте хэш-таблиц и при печати отчёта.

### Тонкие места

- Ключи таблиц указывают в память файла, поэтому `MappedFile` должен жить дольше `Stats`.
- `FlatMap::operator[]` возвращает ссылку, которая перестаёт быть действительной, если в ту же таблицу вставить новый ключ (она может вырасти).
- Корректность без мьютексов держится на том, что файл только читается, каждый поток пишет в свой `Stats`, а видимость результатов даёт `join()`.

## Структура

```
include/le/    time_util.hpp  mapped_file.hpp  flat_map.hpp  parser.hpp  stats.hpp  engine.hpp
src/main.cpp   CLI и отчёт
tools/         gen_logs.cpp, генератор тестовых логов
```

## Ограничения

- Один формат строки, уровень `WARNING` не распознаётся.
- Проверка даты упрощённая (`2026-02-31` пройдёт).
- Файл нельзя изменять или обрезать, пока он отображён в память.
- Протестировано только на Windows (GCC/MinGW). Ветка `mmap` для Linux/macOS написана, но не собиралась.
- Сборка через CMake не проверялась, проверена только прямая сборка `g++`.
